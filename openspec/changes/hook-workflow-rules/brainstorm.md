## Design Summary

The pilot change `hook-delivered-rules` built the hook engine and moved one rule, the commit-type guide. This
change moves the next set of workflow rules to hook delivery and closes the one failure the owner keeps seeing:
after implementation in the superspec workflow, agents stop and ask permission to push and open the pull request,
although finalize is defined to create it without asking.

**Why agents stall.** The owner reports the stall as a recurring observation; no transcript is attached. What the
repository shows:

- The generated `openspec-apply-change` skill ends with "report that tracked tasks are complete and suggest
  review or verification" (its step 7 and output template). `openspec-*` skills are regenerated by
  `openspec update` and must not be hand-edited (capability `openspec-skills-delivery`), so this ending stays.
- The harness's default, as stated in the agent's own system instructions, is to confirm outward-facing actions
  (push, PR) unless durably authorized.
- The authorization exists: `.agents/rules/repo-superspec-closeout.md` is always on and says finalize creates the
  PR without asking. So the problem is not that the text is absent; it is that always-on text, read hours earlier,
  loses at the moment of stopping to the fresher skill ending and the harness default.

The fix therefore puts the text in front of the agent **at the stop**, and keeps the authorization itself in the
always-on pointer. The stop gate and the pointer carry the load; the earlier moments and the config guidance are
reinforcement.

**What this change does:**

1. **A stop gate (a new trigger kind).** When the main agent tries to end its turn while a change it worked on in
   this session has an apply receipt, no failing verify and no finalize receipt, the engine blocks the stop once per
   phase and shows the closeout rule with a line naming the change. Claude Code: a `Stop` hook returning
   `decision: block`. OpenCode: the plugin answers the host's turn-end event (`session.idle` if emitted;
   `session.execution.succeeded` in 2.3.2) with a synthetic prompt carrying the text; this
   is spiked first, and if it does not work the owner decides whether OpenCode is moments-only for the stop gate.
2. **Earlier moments** for the closeout rule: the apply, verify, continue and archive skills and the
   `openspec instructions verify|finalize` commands.
3. **A config layer.** `openspec/config.yaml` apply guidance states that after the tasks are done the agent runs
   verify and finalize without asking, and that finalize creates the PR. This text reaches every
   `openspec instructions apply` output and survives `openspec update`.
4. **Move five more rule files to hooks** (owner's choice): the closeout, the review gate, the reviewer roster,
   real-device testing and pre-push checks. Tracker intake stays always-on.
5. **A budget check** in the agent-file check: for every skill name in any rule and for every command in a fixed
   list of workflow commands (each `openspec instructions <artifact>`, `openspec new change`, and a chained
   verify-then-finalize call), plus the stop text, the matching rule texts must fit the 9,000-byte delivery cap.
   The runtime cap stays the backstop for commands outside the list.
6. **Moments deliver only what is not already live.** Observed in this session: the engine's `decide` adds a
   matching rule's text at every moment, even when the rule is already delivered in that context and generation
   (the commit-types guide was re-sent after each shell call whose text contained `openspec instructions
   finalize`). With six hooked rules sharing moments that repeat (a second skill call or `SKILL.md` read of the
   apply skill re-sends ~7.8 KB; every later shell call whose text holds a command pattern re-sends that rule),
   the repeats add up. A moment now skips a rule only when the same trigger
   already delivered it in this context and generation: each `delivered` entry records the triggers that delivered
   it (a skill name, or the matched `commands` pattern). A repeated `openspec instructions finalize` or a second apply-skill
   moment is skipped; a different moment, such as the verify skill or, after the apply skill, `openspec instructions finalize`, delivers the rule again, so the
   text stays fresh at each distinct step. Compaction re-arms as before.

**Rules that apply outside the workflow.** Real-device testing and pre-push checks apply to every change, not only
to openspec work. Their moments are therefore not only workflow moments: each has a shell gate that every PR or
push passes through (`gh pr create`, `git push`), and each pointer states the rule itself in one line, so the
always-on text loses nothing. Pre-push is moved although it is small because its value is the gate: the per-node
check list is in front of the agent at the push, where it is used. Signing keys has no such command to gate (a key
can be overwritten by any file write), so it stays always-on.

**The brainstorm review moment.** A brainstorm is written through `superpowers:brainstorming`, which is not a
listed skill, but the workflow always runs `openspec instructions brainstorm` first, and that command is a
review-gate moment.

Later candidates, out of scope here: tracker intake through prompt-pattern moments; the Android lint rule as a
`git push` gate limited to changes that touch `android/`; Claude Code `PostToolBatch` to close the same-batch
residual.

## Alternatives Considered

### Alternative A: Moments and config guidance only
- **Approach**: Deliver the closeout rule at the apply, verify and continue moments and add the config apply
  guidance; no stop hook.
- **Pros**: No new trigger kind; no new host wiring; nothing can block a stop.
- **Cons**: The failure happens at the stop. Today the rule is always on and still loses there; delivering it a
  little earlier does not change where it loses.
- **Why not chosen**: It does not act at the moment the mistake is made.

### Alternative B: Stop gate only
- **Approach**: Only the stop gate; rules stay always-on.
- **Pros**: Smallest change for the PR stall.
- **Cons**: The other rules stay always-on, and the owner asked for more rules to move.
- **Why not chosen**: Leaves the second half of the request undone.

### Alternative C: Hand-edit the generated apply skill
- **Approach**: Change the skill's final step to "run verify and finalize".
- **Cons**: `openspec update` overwrites it, and `openspec-skills-delivery` forbids the edit.
- **Why not chosen**: Not durable.

## Agreed Approach

Layers plus a stop gate (owner's choice): config guidance, earlier moments and a stop gate for the closeout rule;
the four other rule files (review gate, roster, real-device, pre-push) move to hooks; the budget check keeps every
moment within the cap. OpenCode gets the stop gate only if a spike shows a turn-end continuation works;
otherwise the owner decides.

## Key Decisions

- **Owner's calls:** the layered approach with the stop gate; moving closeout, review gate, roster, real-device and
  pre-push; tracker intake stays always-on; OpenCode stop parity is spiked first, with a stop for the owner's
  decision if it fails; reviewer preset `opus` for this session.
- **My call — the stop predicate is a named check, not a regex.** A stop has no command text to match; whether a
  change waits for finalize is file state. A new frontmatter key `stops` lists predicate names from a fixed
  registry in the engine; this change adds one, `superspec-finalize-pending`. The restricted grammar is unchanged.
- **My call — which change, and where its files are.** The engine records, per session, the change names it saw in
  successful `openspec` shell calls that carry `--change <name>` (the apply, verify and finalize steps all do).
  At a stop it looks for each recorded change in the event's checkout, the main working tree and every linked worktree of the same
  git common directory (read from the common directory's `worktrees/*/gitdir` files, no subprocess). A recorded
  change is pending when some copy has `apply.md`, no copy has `finalize.md`, no checkout has an archived copy
  (`openspec/changes/archive/<YYYY-MM-DD>-<name>/`), and the `verify.md` next to the newest `apply.md`, if any, does not have
  its FAIL box ticked. "Newest" is the highest `Iteration:` value, and the first copy found in checkout order (the
  event's checkout first) on a tie. The change set is session-wide: a subagent's `--change` call counts for the
  main context's stop. A session with no recorded change is never
  stop-gated, so an unrelated session in a checkout with a paused change is never blocked.
- **My call — once per phase, surviving compaction.** For each change the stop gate fires at most once per
  session and phase, whatever the compactions; the per-phase record, not Claude Code's `stop_hook_active`, bounds it, so a stall
  after a passing verify in the same continued turn is still caught. A phase is
  the newest apply iteration plus whether a passing verify exists for it, so the gate can remind after apply and
  again after a passing verify (the two likeliest stalls), and again at a new apply iteration.
- **My call — the reminder allows a legitimate stop.** The engine's line above the rule text names the change and
  says: run verify if it has not run, then finalize, which pushes and creates the PR without asking; but if a
  rule requires you to ask the user (a device or browser is unavailable, a blocker, an ambiguity) or the user told
  you to stop, say which and end the turn — the next stop is not blocked.
- **My call — subagents are not stop-gated.** Only the main context's stop is gated (`Stop`, not
  `SubagentStop`); implementation subagents must not run finalize. The OpenCode spike checks how a child
  session's turn-end event is told apart.
- **My call — the pointers carry the authorization and the outside-workflow rules.** The closeout pointer states
  that finalize pushes and creates the PR without asking; the real-device and pre-push pointers state their rules
  in one line.
- **My call — de-duplicate per trigger, not per rule.** Only `delivered` entries suppress a repeat; a `pending`
  rule is delivered at a moment and becomes `delivered`, keeping its patterns, so a moment still confirms a
  pending denial and repairs a stale pending entry. A stale delivery now also suppresses repeats of the same
  trigger until compaction; a different trigger still delivers. The stale-credit text in the spec and in
  `docs/hook-delivered-rules.md` is amended to say so, and the end-to-end check adds a moment after a stale
  delivery. The `hooked-rule-delivery` delta therefore also changes the Moments requirement, the "Cap at a moment"
  scenario (the cap counts only rules the moment will send) and the Stale credit wording.
- **My call — what a trigger is, and how entries grow.** A skill trigger is the canonical skill name (an `opsx:<x>`
  name maps to its `openspec-*` skill through a fixed table), so a skill call, a `/opsx:apply` prompt and a
  `SKILL.md` read of the same skill are one trigger. A command trigger is the matched `commands` pattern. Triggers get
  their own `triggers` field, separate from the gate `patterns`; a re-delivery adds to both sets and never
  replaces them.
- **My call — state version 2.** The new fields (`triggers`, the stop records, the session change set) bump the
  state file to version 2. The new engine reads a version 1 file as version 2 with empty new fields; an old
  engine meeting a version 2 file fails open with the read-by-hand notice, as today for any unreadable state. The
  one-time upgrade window is accepted.
- **My call — a stop block is its own record.** A stop-gate block records only the once-per-phase stop entry;
  it does not mark the closeout rule delivered, so later closeout moments still deliver it.
- **My call — the stop gate fails open.** On an engine error, a timeout, a lock timeout or an unreadable receipt
  the stop is allowed; where Claude Code's `Stop` output has a channel, the agent gets the read-by-hand notice.
  The once-per-phase record is written in the same transaction that decides the block.

## Delivery budget

The worst moment is the apply skill: commit types (1,717) + review gate (1,824) + real-device (773) + closeout
(3,523), joined with three blank-line separators, is about 7,843 bytes, under the 9,000-byte cap; the roster is not
delivered there. The continue skill delivers review gate, roster, real-device and closeout: about 7,040 bytes. The
budget check fails the agent-file check when any listed trigger's sum exceeds the cap; the fix is then to shorten a rule
or drop a moment, never to raise the cap.

## Root AGENTS.md line budget

The root is exactly 40 lines. The `## Rules` paragraph shrinks from six content lines to two (three always-on
paths and the path-scoped sentence), saving four; the OpenCode paragraph joins the Rules section without its own
blank line, saving one; five pointer lines are added. Net: 40 lines. Each pointer stays on one line.
