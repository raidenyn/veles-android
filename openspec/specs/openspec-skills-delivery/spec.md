# openspec-skills-delivery Specification

## Purpose
This capability defines how this repository consumes OpenSpec 2.x: skills only, with one generated copy under `.agents/skills/`, per-skill symlinks for Claude Code, no command files and no `.opencode/` tree, an idempotent `openspec update`, and a structural CI check that never installs the OpenSpec CLI.

## Requirements

### Requirement: Supported OpenSpec CLI range
Contributor guidance SHALL state that OpenSpec CLI `>= 2.0.0, < 3` is supported and that 2.0.0 is the last verified version, and SHALL state that 1.x is unsupported for this repository. The repository MUST NOT pin an exact CLI version.

#### Scenario: Newer 2.x
- **WHEN** a contributor runs `openspec update` with a 2.x CLI newer than 2.0.0 and skill text changes
- **THEN** the result is a normal regenerate-skills diff and no check fails

#### Scenario: Version recorded
- **WHEN** the migration is performed
- **THEN** the verification record states the CLI version used

### Requirement: Skills only, one copy
OpenSpec workflows SHALL be delivered only as skills. A single copy MUST exist in `.agents/skills/` generated by `openspec update`, `.claude/skills/<name>` MUST be the symlinks that update creates, and there MUST be no OpenSpec command files and no `.opencode/` tree. A hand edit inside an `openspec-*` skill MUST NOT exist because `openspec update` overwrites it; lasting changes belong in skills whose names do not start with `openspec-` or in `openspec/config.yaml`.

#### Scenario: Migration result
- **WHEN** `openspec update` is run on the 1.x layout with a supported CLI
- **THEN** it deletes `.claude/commands/opsx/*`, `.opencode/commands/*`, `.opencode/skills/*` and the real `.claude/skills/*` directories, adds one `.agents/skills/<skill>` and one `.claude/skills/<skill>` symlink per skill of the contributor's configured workflow list, and the `.agents/skills/.openspec-target` marker, and removes nothing else

#### Scenario: Marker is not a skill
- **WHEN** the check compares `.agents/skills/` with `.claude/skills/`
- **THEN** `.agents/skills/.openspec-target` is excluded because it lists tool IDs and is not skill content

#### Scenario: No command spelling in live files
- **WHEN** live documentation, workflows or the `superspec` instructions and templates are searched
- **THEN** they refer to skills (`/openspec-propose`, `/openspec-apply-change`, …) and not to `/opsx:` commands, while archived and frozen evidence is left unchanged and the resulting fork of the third-party `superspec` schema is recorded in `docs/openspec-workflow.md`

### Requirement: The generated skill set is documented and checked
The set of `openspec-*` skills in `.agents/skills/` depends on the user-wide OpenSpec workflow list, so `docs/openspec-skills.md` SHALL document the required workflow list and the resulting skill names, and the agent-file check MUST read that file and fail when the `openspec-*` skills present differ from the documented list. `docs/AGENTS.md` MUST link `docs/openspec-skills.md`.

#### Scenario: Different workflow list
- **WHEN** a contributor whose workflow list differs runs `openspec update` and commits a different set of skills
- **THEN** the agent-file check fails and names the added or missing skills

#### Scenario: Deliberate change
- **WHEN** a newer 2.x CLI adds a skill and the pull request updates the documented list in `docs/openspec-skills.md` with it
- **THEN** the check passes

### Requirement: Update is idempotent after migration
After the migration commit, a second `openspec update` with the CLI used for the migration MUST change no file, and the verification record MUST show that run. This is verified once at migration and is not a CI step.

#### Scenario: Second run
- **WHEN** `openspec update` is run again after the migration commit
- **THEN** it changes no file

### Requirement: CI checks structure without the OpenSpec CLI
The docs check and `check-docs.yml` SHALL verify the OpenSpec layout structurally and MUST NOT install or require the OpenSpec CLI. A regression to 1.x output MUST be detected through the forbidden legacy paths (`.claude/commands/`, `.opencode/`), and a missing or wrong skill link through the skill-parity check.

#### Scenario: Workflow does not install OpenSpec
- **WHEN** the workflow-contract suite inspects `check-docs.yml`
- **THEN** it fails if the workflow installs the OpenSpec CLI or any other package from a registry at run time

#### Scenario: 1.x regression
- **WHEN** a contributor with OpenSpec 1.x runs `openspec update` and commits `.opencode/`
- **THEN** the agent-file check fails and names the legacy path

### Requirement: OpenSpec updates run on Linux or macOS until Windows is verified
Contributor guidance SHALL state that `openspec update` is run on Linux or macOS until the Windows behaviour with the supported CLI has been verified, and the verification record MUST report the Windows result with symlinks enabled and disabled.

#### Scenario: Windows result recorded
- **WHEN** the verification record is read
- **THEN** it states what `openspec update` did on Windows with `core.symlinks` true and false, or that the run could not be made
