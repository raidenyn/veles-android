# Connector-tab Web Bluetooth spike - physical validation report

## Status

**Physical summary recorded; matrix incomplete.** Core transport behavior was
spot-checked on Windows, macOS, and two Android phones. The 20-minute lifecycle
and two-connector topology were not tested, background-tab behavior was not
tested against the stable product requirement, and exact environment/version
data was not recorded.

The current product roadmap removes OS Bluetooth pairing as a prerequisite,
uses plain GATT only as untrusted transport, and requires an open connector tab
to stay useful while backgrounded. This report preserves the observations that
caused those decisions; it does not convert missing evidence into a pass.

This report was generated by the implementation environment, which has no
access to the required physical Windows, macOS, and Android hardware matrix, so
hardware-dependent fields originally started as `Not run`. The tester later
provided an abbreviated result summary rather than a case-by-case form. The
table below records only what that summary establishes and keeps omitted cases
explicitly untested.

The two platform findings below record behavior observed during exploratory
debugging. They establish why the launch context and link-layer security model
changed. The later abbreviated summary provides the limited case evidence
recorded in the matrix.

The implementation-environment automated tests (debug JVM tests,
`./gradlew assembleDebug`, `./gradlew assembleRelease`) validate construction
only. They do not validate Web Bluetooth behavior on any physical platform.

## Action-popup platform finding

The initial physical attempt called `navigator.bluetooth.requestDevice()`
directly from the action popup's Connect button. Chrome displayed no chooser
and rejected the promise with `NotFoundError: User cancelled the
requestDevice() chooser.`

Chromium's extension chooser implementation requires the requesting extension
document to be the active contents of a browser tab. An action popup is not a
tab, so Chrome returns without showing the chooser and reports cancellation
when the chooser controller is destroyed. The harness now opens the same
connector document in an extension tab. Results below apply only to that
revised launch context.

## Windows BLE pairing platform finding

The spike originally required an authenticated (MITM-protected) link, declaring
`PERMISSION_*_ENCRYPTED_MITM` on both characteristics and on the CCC descriptor.
Physical testing on Windows could not complete a connection under that
requirement, across two Android phones and every combination of pairing state we
could construct.

Observed on Windows 11 with stable Chrome, confirmed against `BTHPORT`/`BTHUSB`
ETW traces decoded to HCI/L2CAP/SMP/ATT level:

- **Already-bonded phone.** Encryption is re-established from the stored key
  (`Encryption Change status=0x00 ... enabled=1`) and GATT discovery completes:
  Chrome finds the spike service, both characteristics, and the CCC descriptor.
  The first ATT **read of an MITM-gated attribute value** then receives no
  response at all — no `Insufficient Authentication` error, just silence — until
  Windows tears the link down after 21-31 s. Chrome surfaces `NetworkError: GATT
  Server is disconnected.`
- **Fresh, never-paired phone.** The SMP handshake runs correctly through
  `Pairing Request/Response`, both `Pairing Public Key` exchanges, `Pairing
  Confirm`, and both `Pairing Random` messages. Chrome rejects the JS promise
  with `NetworkError: Authentication failed` at the exact millisecond the
  numeric comparison value becomes computable — before a user could physically
  confirm it. The OS-level negotiation continues underneath for a further 30 s,
  so the phone's pairing dialog appears and can be confirmed successfully, but
  the page has already given up.
- **Windows never surfaced its own comparison prompt** for pairing initiated
  in-band by Chrome, though pairing the same phone explicitly through Windows
  Settings shows matching codes on both devices and completes normally.
- **Residual state.** After a failed attempt, subsequent attempts fail with
  `NetworkError: Connection already in progress`, or hang on "Connecting…"
  indefinitely while issuing no HCI command whatsoever. This survives closing
  the tab, reloading the extension, and fully restarting Chrome.
- `Get-PnpDevice` shows the phone with no cached GATT service child devices,
  unlike BLE peripherals that have completed discovery on this host.

Dropping to plain `PERMISSION_READ`/`PERMISSION_WRITE` makes the same phone,
host, and build connect, subscribe, authenticate, and deliver a synthetic OTP
immediately, with no pairing prompt. That isolates the failure to Chrome's
handling of pairing-gated GATT access on Windows rather than to the harness, the
protocol, the phone, or the bond.

**Consequence for the design.** BLE link-layer security cannot be relied on for
this feature without excluding Windows users, so the spike now runs with no
link-layer protection and synthetic data only. Confidentiality and MITM
resistance for real OTP traffic have to move into the application layer. That
work is **not implemented** and must be completed before any real OTP crosses
this transport. The approved design is in
`docs/superpowers/specs/2026-08-14-bluetooth-application-security-design.md`:

- One-time OPAQUE pairing bound to the phone's short code.
- Persistent non-exportable installation identity keys and explicit per-peer
  revocation, so later connections require no app-level pairing challenge.
- Fresh signed ECDH and directional AEAD traffic keys on every connection.
- Encryption and strict replay protection for every application record,
  replacing the current public test key and plaintext payloads.

Until that exists, this harness must keep carrying synthetic data only.

## Current harness limitations

Moving from an action popup to a tab exposed two limitations in the current
synthetic harness. They are not acceptable assumptions for the stable product:

- **Timer throttling.** Chrome throttles `setInterval` in hidden/backgrounded
  tabs, down to about once per minute after roughly 5 minutes hidden. The
  spike's heartbeat runs every 5 s (`popup.mjs`'s `HEARTBEAT_INTERVAL_MS`)
  against a 15 s server-side timeout (`SpikeSessionRegistry.HEARTBEAT_TIMEOUT_MILLIS`),
  and Web Bluetooth is not on Chrome's throttling-exemption list, so a
  backgrounded connector tab can silently disconnect a session.
- **Clipboard focus requirement.** `navigator.clipboard.writeText()` requires
  the document to be focused; a backgrounded tab is not, so an async copy
  attempted while the connector tab is backgrounded can reject with a
  focus-related error.

Cases already recorded with this harness kept the connector tab visible and
focused. A revised harness must remove the short-timer dependency and route
automatic copy through the supported offscreen clipboard helper. It must then
test background operation as a pass/fail product requirement.

## Observed limitations

- Windows Chrome cannot reliably access MITM-protected GATT attributes.
- A pre-existing Windows bond was associated with failures, but the missing
  environment and run-order evidence does not establish a general rule.
- Windows functional scenarios passed only after changing to plain GATT
  permissions.
- macOS did not reproduce either Windows connection limitation.
- Application-layer confidentiality, peer trust, and replay protection are not
  implemented in the spike, so it remains synthetic-only.

## Environment failures

- Exact hardware, OS, adapter, Chrome version, tested commit, detailed timing,
  and individual repetition records were not supplied.
- The 20-minute lifecycle, two-connector topology, repeated-action behavior,
  and production-grade background-tab behavior were not tested.

## Decision

**Conditionally promising but incomplete.** Tab-owned plain-GATT Web Bluetooth is usable
for the tested pull, push, clipboard, closure, and two-phone flows. Windows
rules out relying on BLE MITM permissions. Pre-existing bond behavior remains
unresolved, and normal setup no longer requires a bond. The required
two-connector, background-tab, and 20-minute lifecycle cases remain untested.

Proceed to an application-layer security prototype using one-time trusted
pairing, persistent per-installation identity keys, fresh authenticated session
keys, AEAD, and replay protection. Do not send real OTPs until that protocol is
implemented, reviewed, and physically validated. The original all-cases `Go`
threshold has not been met.

## Go / no-go rules

The rules below are copied from the approved spec
(`docs/superpowers/specs/2026-08-11-popup-web-bluetooth-spike-design.md`,
"Decision rule"). Apply them only after the matrix has been run and the
observed values populated.

- **Go** only when every core case passes on stable Chrome for both supported
  desktop operating systems. Prompt wording differences and a measured bounded
  disconnect delay may be recorded as non-blocking limitations.
- **No-go** on a repeatable connector-tab failure of chooser/pairing survival,
  authenticated pull/push, background delivery and copy, explicit reselection,
  either required multi-device topology, or the foreground-service lifecycle.
  Popup-owned Web Bluetooth has already been ruled out by the action-popup
  platform finding above.
- A harness defect is fixed and retested rather than counted as a platform
  failure.
- A result blocked by unavailable hardware, an unidentified environment
  problem, or an unresolved harness problem is **inconclusive**, never go.
- Experimental offscreen APIs are not an automatic or tested fallback.

## Notes on construction-only validation

The following automated checks validate construction only and do not
substitute for physical validation:

- `./gradlew testDebugUnitTest` — transport-independent Android logic
  (framing, HMAC proofs, session registry, fan-out).
- `./gradlew assembleDebug` — debug APK builds and contains the spike harness.
- `./gradlew assembleRelease` — release APK builds and does not contain the
  spike activity, service, Bluetooth permissions, or debug package.

In the implementation environment, `node --test spikes/web-bluetooth-popup/protocol.test.mjs spikes/web-bluetooth-popup/launcher.test.mjs`
and `node --check` on each `.mjs` file were run. No browser-based check (no
unpacked-extension load, no popup/connector-tab console-error check) was
performed here — the implementation environment has no Chrome browser; only
the physical matrix can validate that.
