# OTP-01: Add reproducible Chrome and cryptographic toolchains to Gradle — design

Status: Draft
Issue: raidenyn/veles-android#80
RFC: docs/rfcs/2026-08-21-otp-external-devices.md, section `### OTP-01`
Gate: Gate A (protocol and toolchain foundation)

## Purpose

Give the repository a deterministic way to install, lint, type-check, test,
build, and package the TypeScript MV3 extension, the Rust core placeholder
crate used to validate JNI and WASM plumbing (the real SPAKE2 core lands in
OTP-03), and the unsigned Tauri native-bridge release
inputs for Windows and macOS — all exposed through consumer-native CI-safe
entry points, all pinned, and all byte-reproducible in clean environments.
Rust/native tooling integrates with Gradle; the standalone extension uses npm.

OTP-01 delivers the toolchain foundation that Gate A and every later OTP task
depend on. It contains **no** Bluetooth transport, **no** cryptographic
protocol behavior, **no** UI, and **no** real OTP integration (RFC
"Exclusions" — preserved verbatim here as the acceptance boundary).

## Classified path

Architectural → decomposed into four sub-projects per user decision. Each
sub-project gets its own spec→plan→implement cycle. This document is the
single OTP-01 decomposition spec. Sub-projects 1a and 1b are designed in full;
1c and 1d remain at boundary level until their respective cycles begin.

## Sub-projects and sequencing

| # | Sub-project | Deliverable | Feed into |
|---|---|---|---|
| 1a | TS/MV3 extension toolchain | `web-extension/` npm/Vite project + deterministic zip | OTP-02, 05, 07, 17, 18 |
| 1b | Rust core + JNI/WASM | `rust/` workspace, jniLibs for Android ABIs, `web-extension/rust-wasm/pkg` | OTP-02→03, 06 |
| 1c | Tauri native-host packaging | unsigned Windows/macOS bridge binaries, host manifests, per-user installer inputs | OTP-23, 24, 25 |
| 1d | Verification & supply chain | `verify/` extension + SBOM + license + byte-compare harness | Gate A, Gate D |

Canonical order: **1a → 1b → 1c → 1d**. Rationale: each sub-project must
leave artifacts in place for the next to consume; 1d verifies all three and
therefore cannot close until build outputs exist.

## Global decisions (apply to 1a / 1b / 1c / 1d)

1. **Base toolchain provisioning is PATH-based, minimum-version declared only
   for Node.** node/npm/rustup/cargo are not downloaded by Gradle. The single
   Node floor is `engines.node = ">=22.0.0"` in
   `web-extension/package.json`; npm is bundled with Node and its version is
   only logged for diagnosis (no separate `engines.npm` entry).
   `rust/rust-toolchain.toml` pins Rust and its components/targets. Gradle's
   `rustInstall` may use that pinned Cargo to install exact-version auxiliary
   build CLIs under `build/rust-tools/`; it never installs Rust or rustup.
   `verify/` Docker images bake exact runtime versions for byte-compare
   environments; developer machines need only satisfy the declared Node floor
   and provide rustup/cargo when building APK or Rust artifacts.
2. **Lockfiles are the reproducibility contract.** `package-lock.json` and
   `Cargo.lock` are committed and builds run `--locked` / `npm ci`. Drift
   fails the build; never auto-fixed in CI.
3. **Artifacts under `build/`, with two named exceptions.** Generated Gradle
   outputs land under root or module `build/` directories and are wiped by
   `clean`. Two
   deliberate exceptions exist where a consumer outside Gradle expects a
   path inside a source tree:
    - `web-extension/dist/` — Vite's conventional output, produced by
      `npm run build`/`npm run package`. Beginning with 1b, root `clean` is
      extended to also delete this directory.
   - `web-extension/rust-wasm/pkg/` — Vite expects WASM imports inside the
      project tree. Gitignored; regenerated by `rustWasm` (1b) before a future
      extension import consumes it.
   No other generated artifacts live outside `build/`.
4. **Each toolchain uses its consumer's native entry point and a dedicated CI
   job.** The extension remains npm-native because it never enters the APK;
   its `format:check`, `lint`, `typecheck`, and `test` scripts run in the
   `web-extension` CI job. Rust and native-bridge tasks integrate with Gradle;
   their format/lint/test tasks join root `check`, and each sub-project gets a
   dedicated job in `.github/workflows/ci.yml`.
5. **The APK remains a single Gradle project, but JNI makes Rust part of APK
   assembly beginning with 1b.** No new Gradle subprojects are added under
   `settings.gradle.kts` (`:app` remains the only included project). Rust and
   later native-bridge/verification tasks live in root `build.gradle.kts`.
   Extension entry points remain npm scripts. Once 1b lands, a clean
   `:app:assembleDebug` or `:app:assembleRelease` requires rustup/cargo and the
   pinned NDK so every APK reliably contains the generated JNI library.

## Sub-project 1a: TypeScript/MV3 extension toolchain (implemented design)

Sub-project 1a landed in PR #107. `web-extension/` is a standalone npm/Vite
project with background, content, options, and popup entries; a TypeScript
manifest generator; strict TypeScript/ESLint/Prettier configuration; smoke,
manifest-guard, and bundle tests; exact dependency pins; and a committed
`package-lock.json`.

The extension deliberately has no Gradle wrappers because it never integrates
with the APK. Its supported entry points are:

| Command | Behavior |
|---|---|
| `npm ci` | Installs exactly the committed lockfile. |
| `npm run format:check` | Checks Prettier formatting. |
| `npm run lint` | Runs ESLint. |
| `npm run typecheck` | Runs TypeScript without emitting. |
| `npm test` | Runs source smoke and exact manifest-policy tests. |
| `npm run build` | Builds the unpacked extension to `web-extension/dist/`. |
| `npm run test:bundle` | Checks the exact built file set and generated manifest. |
| `npm run package` | Builds and creates the deterministic ZIP plus SHA-256 sidecar under root `build/web-extension/`. |

`scripts/package.mjs` sorts ZIP entries, fixes timestamps and Unix modes,
excludes undeclared files/directories, writes the ZIP with deterministic
metadata, and emits its lowercase hexadecimal SHA-256 sidecar. The artifact
name uses `web-extension/package.json`'s version, independent of Android's
git-derived version. `manifest-guard.test.ts` enforces exact permissions,
host-permission absence, and CSP; `bundle.test.ts` checks the built file
allow-list and manifest round-trip.

The `web-extension` CI job uses Node 22, runs every quality/build/package entry
point directly through npm, and uploads `build/web-extension/`. Lock drift,
format/lint/type failures, manifest-policy drift, unexpected bundle files, or
package drift are hard failures. Byte comparison across clean reference
environments remains 1d scope.

## Sub-project 1b: Rust core + JNI/WASM (full design)

### Purpose and boundary

Prove that one locked Rust implementation can execute through Android JNI and
browser-shaped WASM bindings, and make those artifacts reproducible inputs to
the APK and extension trees. The implementation is deliberately disposable:
OTP-03 replaces the placeholder core and binding API after OTP-02 freezes the
real protocol.

1b contains no SPAKE2, cryptographic semantics, keys, randomness, protocol
state, Bluetooth, OTP integration, extension runtime call site, or UI. Its only
operation reverses an arbitrary input byte sequence. Reversal is
length-preserving, deterministic, handles empty/non-UTF-8 input, adds no crypto
dependency, and carries no security meaning.

### Layout and ownership

```
rust/
  Cargo.toml                         # workspace containing veles-crypto only
  Cargo.lock                         # committed dependency lock
  rust-toolchain.toml                # Rust 1.98.0 + components/targets
  toolchain-tools.toml               # exact auxiliary CLI pins
  veles-crypto/
    Cargo.toml                       # rlib + cdylib
    src/lib.rs                       # core plus target-gated JNI/WASM exports
    tests/wasm-smoke.mjs             # executes generated web binding in Node
app/src/main/java/me/nagaev/veles/crypto/
  VelesCrypto.kt                     # minimal System.loadLibrary/JNI wrapper
app/src/androidTest/java/me/nagaev/veles/crypto/
  VelesCryptoInstrumentedTest.kt     # calls the packaged x86_64 .so
```

Generated output boundaries are:

```
build/rust/target/                         # all Cargo compilation output
build/rust-tools/<tool>/                   # non-overlapping Gradle-installed CLIs
app/build/generated/jniLibs/<abi>/         # APK JNI inputs
web-extension/rust-wasm/pkg/               # generated web WASM package
```

Only `web-extension/rust-wasm/pkg/` is a new named exception to the root
`build/` output policy, and it is gitignored. No generated file is written to
`app/src/main/jniLibs/` or committed.

### Crate and binding design

`veles-crypto` declares `crate-type = ["rlib", "cdylib"]` and keeps one shared
`reverse_bytes(&[u8]) -> Vec<u8>` implementation. The `jni` dependency and JNI
export compile only for Android; `wasm-bindgen` and its export compile only for
`wasm32`. This keeps both foreign interfaces in one crate without making either
platform carry the other's dependency.

The Android surface is the single Kotlin method
`VelesCrypto.reverseBytes(ByteArray): ByteArray`. Its corresponding
`extern "system"` JNI symbol converts `jbyteArray` to Rust bytes, calls the
shared function, and creates a new `jbyteArray`. `rustJni` scopes
`CARGO_PROFILE_RELEASE_PANIC=unwind` to its cargo-ndk process, and the shim
catches ordinary Rust unwinds. `rustWasm` never inherits that environment and
keeps the stable wasm32 target's abort panic strategy. A caught JNI panic or JNI
error without an existing pending Java exception becomes a generic Java
exception and a null return; an existing pending exception (including
`OutOfMemoryError`) is preserved. Rust allocator exhaustion may still abort and
is not claimed recoverable. Messages do not contain input bytes, and no unwind
crosses the JNI boundary.

The WASM surface is one `wasm-bindgen` byte-array export backed by the same
shared function. `wasm-pack --target web` generates ES-module JavaScript,
TypeScript declarations, and the `.wasm` file. The Node smoke test reads the
generated `.wasm` bytes, initializes that exact web-target module, and invokes
the generated export with a `Uint8Array`; it does not substitute a Node-target
build or mock.

The workspace pins exact direct dependency versions and commits `Cargo.lock`.
The initial reviewed toolchain set is Rust `1.98.0`, `cargo-ndk` `4.1.2`,
`wasm-pack` `0.15.0`, `wasm-bindgen`/`wasm-bindgen-cli` `0.2.127`, and `jni`
`0.22.4`. `toolchain-tools.toml` pins auxiliary CLI versions for Gradle and CI
cache keys; installation also verifies that `wasm-bindgen-cli` exactly matches
the workspace's locked `wasm-bindgen` version.

### Android/NDK integration

`libs.versions.toml` pins stable NDK r29 as `ndk = "29.0.14206865"`, and
`app/build.gradle.kts` assigns `android.ndkVersion` from that catalog entry.
The app registers `app/build/generated/jniLibs` as a `main` JNI source directory
and applies app-level ABI filters for exactly `arm64-v8a`, `armeabi-v7a`, and
`x86_64`. These filters also remove the existing dependency-provided `x86`
libraries, making the RFC's APK ABI allow-list true for all native content, not
only the Rust library. Android JNI merge tasks depend on root `rustJni`; task
ordering never relies on files left by an earlier command. `rustJni` obtains
AGP's NDK directory provider for the app configured with `android.ndkVersion`,
validates that `source.properties` reports exactly `29.0.14206865`, and sets
that canonical directory as `ANDROID_NDK_HOME` for `cargo-ndk`. It never allows
cargo-ndk to auto-select the newest installed NDK.

The generated JNI source directory contains exactly:

```
arm64-v8a/libveles_crypto.so
armeabi-v7a/libveles_crypto.so
x86_64/libveles_crypto.so
```

Every clean debug and release APK requires Rust plus the pinned NDK and contains
exactly these Veles JNI ZIP entries:

```
lib/arm64-v8a/libveles_crypto.so
lib/armeabi-v7a/libveles_crypto.so
lib/x86_64/libveles_crypto.so
```

Locked third-party native entries may also exist, but only under those three
approved ABI directories.

`cargo-ndk` receives Android platform 33, matching the app's minSdk, and the
NDK directory resolved from the Android SDK/AGP configuration. It invokes
Cargo's Android target builds and writes directly into the generated JNI
source directory. There are no `x86`, `riscv64`, or host libraries.

### Gradle tasks

The root build applies Gradle's `base` plugin to own root `check` and `clean`.
Public tasks use group `rust`:

| Task | Command/behavior | Dependencies | Output |
|---|---|---|---|
| `rustInstall` | Validates rustup/cargo and `rust-toolchain.toml`, then installs exact-pinned auxiliary CLIs with `cargo install --locked` under per-tool roots | internal Android/WASM tool install tasks | `build/rust-tools/<tool>/` |
| `rustJni` | Local `cargo-ndk` release build, platform 33, three approved ABIs, workspace `--locked` | Android tool install task | `app/build/generated/jniLibs/` |
| `rustWasm` | Local `wasm-pack build veles-crypto --target web --release --mode no-install --no-opt --out-dir <absolute-pkg-dir> -- --locked` | WASM tool install task | `web-extension/rust-wasm/pkg/` |
| `rustFormat` | `cargo fmt --all -- --check` | toolchain validation | — |
| `rustLint` | Runs host, `wasm32-unknown-unknown`, and Android x86_64 Clippy checks with `--locked` and `-D warnings` | toolchain validation, Android tool install task | — |
| `rustTest` | Native `cargo test --workspace --locked`, then Node smoke test against `rustWasm` output | toolchain validation, `rustWasm` | — |

Internal install tasks use separate roots for `cargo-ndk`, `wasm-pack`, and
`wasm-bindgen-cli`, preventing overlapping Gradle outputs and concurrent Cargo
installation metadata writes. They keep `rustJni` from compiling WASM-only CLIs
and keep `rustWasm` from installing `cargo-ndk`; `rustInstall` remains the
documented aggregate entry point. Every Cargo command sets `CARGO_TARGET_DIR`
beneath `build/rust/`. Install tasks include their pins and `Cargo.lock` where
relevant as inputs and verify restored/cached binary versions before declaring
success.

`wasm-pack` runs in `no-install` mode with the matching local
`wasm-bindgen-cli`, and `--no-opt` prevents an implicit Binaryen/`wasm-opt`
download. `rustWasm` prepends the per-tool `wasm-pack` and
`wasm-bindgen-cli` binary directories to its process PATH. Its Gradle-computed
absolute `--out-dir` is `web-extension/rust-wasm/pkg/`; `-- --locked` is passed
only to Cargo after all wasm-pack options. Workspace builds use `--locked`;
lock drift is never repaired. Root `check` depends on `rustFormat`, `rustLint`,
and `rustTest`. Root `clean` removes root/app build outputs,
`web-extension/dist/`, and `web-extension/rust-wasm/pkg/`.

### Extension boundary and CSP

1b does not add a production import of the generated package. The package path
is established and runtime-tested so a later extension task can consume it
without changing the Rust build contract. The MV3 manifest nevertheless adopts
the approved 1b WASM baseline now. Its exact extension-page CSP becomes:

```
script-src 'self' 'wasm-unsafe-eval'; object-src 'self'
```

The TypeScript manifest guard and bundle test require exact equality: no remote
source, additional directive, host permission, or ordinary `unsafe-eval` is
allowed.

### CI and reproducible environments

The dedicated `rust` CI job provisions JDK 21, Node 22, Gradle, the Rust
toolchain declared in `rust-toolchain.toml`, and NDK r29. Workflow setup obtains
the NDK value from a quiet Gradle print task backed by `libs.versions.toml`
rather than duplicating the version in YAML. Gradle passes AGP's exact NDK
directory to cargo-ndk in every CI/release/verifier invocation; merely having
r29 installed is not treated as selection.

The job runs format, target-complete lint, native/WASM tests, and
`:app:assembleDebug`. APK inspection asserts that the complete native ABI
directory set is exactly `arm64-v8a`, `armeabi-v7a`, and `x86_64`, and that the
complete `libveles_crypto.so` entry set is exactly the three native ZIP entries
listed above. Locked third-party native libraries are permitted only inside
those approved ABI directories. It then exercises clean semantics explicitly:
after creating root/app/tool/WASM outputs and running `npm ci && npm run build`
to create `web-extension/dist/`, it runs `./gradlew clean`, asserts every
declared generated directory is absent, rebuilds `:app:assembleDebug` without
prior task state, and repeats both APK assertions. It finally runs
`rustInstall` to repopulate all per-tool directories before the CI cache-save
phase; clean-test ordering therefore does not discard first-fill WASM tools.

The existing instrumented-test job gains the same Rust/NDK setup and executes
the Kotlin-to-JNI test on its x86_64 emulator. Both release workflows provision
Rust/NDK before `assembleRelease`; they do not provision Node or WASM tooling.
`verify/Dockerfile` gains pinned Rust 1.98.0 and NDK r29 because the existing
zero-trust APK rebuild now compiles JNI. Sub-project 1d may later factor Rust
artifact byte-comparison into its planned `verify/Dockerfile.rust`, but 1b must
not leave the current APK verifier broken.

CI may cache the per-tool directories under `build/rust-tools/` using runner
OS, runner architecture, and hashes of `rust-toolchain.toml`,
`toolchain-tools.toml`, and `Cargo.lock`. Cache misses affect duration, not
correctness: Gradle reinstalls exact versions. Restored tools are
version-checked before use.

### Testing and acceptance

- Native Rust unit tests cover known, empty, and arbitrary non-UTF-8 byte
  fixtures.
- The Node smoke test initializes the generated web-target WASM and verifies
  those fixtures through the `wasm-bindgen` export.
- The Android instrumented test verifies the same fixtures through Kotlin and
  the packaged JNI library on x86_64.
- CI executes every public Rust quality task, proves root `clean` removes all
  declared generated outputs, rebuilds an APK without prior task state, and
  enforces both the complete APK ABI-directory set and exact Veles JNI entry
  set.
- Existing extension source and bundle tests enforce the revised exact CSP.

1b is accepted when all layers pass; generated artifacts live only in their
declared directories; clean APK assembly reliably rebuilds and packages all
three JNI ABIs; app-level filters exclude every other ABI (including the
dependency-provided baseline `x86` libraries); clean removes every generated
output; and neither source nor artifacts introduce protocol behavior, secrets,
remote runtime code, or an undeclared ABI.

### Failure behavior

| Failure | Behavior |
|---|---|
| rustup/cargo missing | Fail before installation/build, naming `rust/rust-toolchain.toml` and the missing PATH tool. |
| Pinned Rust target/component absent | rustup honors `rust-toolchain.toml`; provisioning failure is fatal and identifies the target/component. |
| NDK r29 absent | Fail with `29.0.14206865` and the exact SDK-manager install command; never select another installed NDK. |
| Auxiliary CLI install/version mismatch | Fail; no floating-version or system-binary fallback. |
| Workspace lock drift | Cargo `--locked` fails; no lockfile rewrite. |
| Hidden WASM helper unavailable | `--mode no-install --no-opt` fails rather than downloading a binary. |
| JNI conversion/allocation/panic failure | Preserve an existing pending Java exception; otherwise throw a generic exception without input bytes. Catch ordinary unwinds; allocator abort remains unrecoverable. |
| Node missing or major version below 22 for WASM smoke test | `rustTest` checks `node --version` first and fails with the actual/required version and `web-extension/package.json` engine source. |
| Stale generated output | Producer replaces its output directory before publication so removed ABIs/files cannot survive. |

## Sub-project 1c: Tauri native-host packaging (boundary)

- **Layout:** `native-bridge/` at repo root, a Tauri 2.x headless app
  (`src-tauri/`, `tauri.conf.json`, minimal `index.html` as a placeholder
  entry that is never shown).
- **User-confirmed posture:** Tauri configured with **`windows = []`** and
  all default features disabled (per decision "Tauri headless lifecycle"
  assessed at Gate D). No tray, no menu, no autostart, no login item. The
  process exits on stdin EOF, matching Native Messaging semantics.
- **Toolchain:** `tauri.conf.json`'s own npm devDeps follow the same
  `engines.node` minimum + committed `package-lock.json` pattern as 1a.
- **Gradle tasks (group `native-bridge`):**
  - `bridgeInstall` (`npm ci` inside `native-bridge/`), `bridgeFormat`,
    `bridgeLint`, `bridgeTypecheck` if any TS config, `bridgeTest`
    (`cargo test --locked` inside `src-tauri/`).
  - `bridgeBuild` — raw unsigned host build via
    `cargo tauri build --no-bundle -- --locked`.
  - `bridgePackage` — a separate unsigned bundle invocation plus
    platform-specific deterministic packaging:
    - **Windows:** zip payload containing the `.exe`, native-messaging
      host manifest JSON, and installer inputs (WiX / NSIS files Tauri
      emits) into `build/native-bridge/windows/`.
    - **macOS:** tar payload containing the `.app` bundle (unsigned),
      host manifest, installer inputs into `build/native-bridge/macos/`.
    Exact non-interactive/no-sign bundle flags are deferred to 1c's full
    design; `--no-bundle` output is not treated as installer input.
  - `bridgeManifests` — emits the Chrome native-messaging host manifest
    for each OS with exact host-origin fields pinned to the extension ID
    placeholder used in 1a.
- **Explicitly excluded:** no BLE calls, no crypto, no signed artifacts.
  Tauri signing env vars (`TAURI_SIGNING_PRIVATE_KEY` etc.) are documented
  as absent in CI. `tauri.conf.json` hard-codes unsigned output.

## Sub-project 1d: Verification & supply chain

- **Environment strategy is asymmetric, matching technical reality.** Pure
  Linux-side toolchains (Android via existing `verify/Dockerfile`, plus new
  `verify/Dockerfile.web` for the extension and `verify/Dockerfile.rust`
  for the Rust core) run inside Docker as full reference environments, giving
  byte-stable rebuilds of the extension zip and of the Rust `.so` / `.wasm`
  intermediates. Windows and macOS artifacts cannot be rebuilt inside Linux
  Docker (signing/notarization require Apple/MS SDKs that are not portable),
  so 1d treats **pinned** GitHub-hosted runner labels (`windows-2022`,
  `macos-15` — never `-latest`) as the *documented environments*. Each
  reference run pins (a) the versioned runner label from the workflow YAML,
  (b) the Rust toolchain via `rust-toolchain.toml`, (c) the Tauri CLI
  version from `package-lock.json`, and (d) on macOS the Xcode/SDK version
  explicit in the workflow YAML. Each run captures the observed runner
  image identity from the **`ImageOS` and `ImageVersion` environment
  variables the runner images export** (these are *not* properties of the
  GitHub Actions `runner` context — workflows read them as
  `$env:ImageOS` / `$env:ImageVersion` on Windows and `$ImageOS` /
  `$ImageVersion` on macOS/Linux) plus `RUNNER_ARCH`, asserts all three are
  non-empty, and records them into the workflow log and into
  `SHA256SUMS.native-bridge` metadata. Byte-comparison across two CI runs
  proceeds only when all three recorded values match; on mismatch the
  comparison aborts with a "re-run on matched image" instruction. This is
  deliberately weaker than pinning a self-hosted image ID — that option is
  an extension point if self-hosted infrastructure becomes available
  later.
- **Compare script:** `verify/verify-all.sh` orchestrates: build in each
  Docker image on Linux and compare hashes; run the Windows and macOS CI
  jobs twice on the same **versioned runner label** (`windows-2022`,
  `macos-15`) and compare output hashes **only when the observed image
  identities match** (see the 1d environment-strategy bullet for how
  identity is captured). Mismatch aborts with a re-run instruction. Verify
  the aggregated results against `SHA256SUMS.toolchains`. Exit codes
  mirror `verify.sh` (0 match, 1 mismatch, 2 usage/pin error).
- **SBOM:** `cyclonedx-npm` for `web-extension/`, `cargo cyclonedx` for
  `rust/` and `native-bridge/src-tauri/`. Output JSON files into
  `build/sbom/{web-extension,rust,native-bridge}.cdx.json`.
- **License:** `license-checker-rseidelsohn` for npm, `cargo deny
  licenses` for Rust. Both operate on an explicit, reviewed policy written
  as SPDX allow/deny lists (not a hand-waved "no copyleft" rule). Default
  posture: strong copyleft (GPL-*, AGPL-*, LGPL-* without static-linking
  exception), source-availability (SSPL, BUSL, Elastic), and public-domain
  dedications (CC0, Unlicense) default-deny; permissive (MIT, Apache-2.0,
  BSD-*, ISC, Zlib) default-allow; anything unrecognised fails with the
  license text and a link to the allowlist file so the reviewer can decide
  consciously. Policy file lives at the repo root (`licenses.toml` for
  cargo-deny, `.license-policy.json` for license-checker) and is part of
  the 1d review surface.
- **Checksums:** `SHA256SUMS` files per artifact tree produced by the
  `*Package` tasks, uploaded as CI artifacts.

## Acceptance criteria (traceable to RFC OTP-01)

The RFC's acceptance paragraph has six clauses. OTP-01 closes when the four
clauses it owns (1, 2, 3, 6) are demonstrated. Clauses 4 and 5 are formally
**transferred to OTP-25's acceptance criteria** by the RFC amendment dated
2026-08-26 — they depend on real signing/notarization infrastructure that
is OTP-25 scope. This transfer avoids the dependency deadlock that would
otherwise arise: OTP-25 transitively depends on OTP-01 via
OTP-06/OTP-07/OTP-24,
so if OTP-01 could not close until OTP-25 finished, neither issue could
ever reach Ready in the RFC's dependency model. OTP-01's contribution to
clauses 4 and 5 is the stable unsigned-artifact ground truth and the
no-embedded-secrets guarantee. The amendment is recorded in the RFC
(after the OTP-01 entry's project fields) and on issue #80 so the
transfer is explicit, not silent.

| Clause | Owner | OTP-01 acceptance depends on it? |
|---|---|---|
| 1 (byte-identical artifacts in clean envs) | 1d (`verify-all.sh`) | **Yes** — OTP-01 closes when met |
| 2 (CI-safe build entry points) | 1a npm + 1b/1c Gradle, wired into CI by 1d | **Yes** |
| 3 (artifact content allow-list) | 1a (ext file-set) + 1b (APK ABIs) + 1c (bridge) | **Yes** |
| 4 (signing consumes CI credentials) | OTP-25 | **No** — transferred to OTP-25 |
| 5 (signed↔unsigned correspondence) | OTP-25 | **No** — transferred to OTP-25 |
| 6 (no runtime download / remote exec) | 1a+1b+1c, scanned by 1d | **Yes** |

### RFC clauses (verbatim), with sub-project mapping

1. *"Independent clean documented environments produce matching locked
   dependencies and byte-identical unsigned bridge binaries, bundle/package
   payloads, host manifests, and installer inputs."*
   → **1d.** For Linux-side artifacts (Android APK, extension ZIP, Rust
   `.so`/`.wasm`), `verify/verify-all.sh` builds in pinned Docker
   environments and compares hashes. For Windows/macOS — which cannot be
   reproduced inside Linux Docker — two CI runs on GitHub-hosted
   `windows-2022` and `macos-15` runners record their observed image
   identity via the `ImageOS`, `ImageVersion`, and `RUNNER_ARCH`
   environment variables the images export (these are *not* GitHub Actions
   `runner` context properties), assert all three are non-empty, and
   byte-compare outputs only when the full triple matches; on mismatch the
   verification aborts with a re-run instruction. No claim is made that a
   workflow can pin the underlying image SHA; the check is post-hoc
   identity of environments.
2. *"Gradle exposes CI-safe entry points."*
   → Per the RFC amendment, **1a** exposes npm-native entry points because the
   extension does not integrate with the APK; **1b / 1c** deliver Gradle task
   groups. **1d** wires `verify-all.sh` byte-compare into CI and asserts all
   entry points run without interactive input.
3. *"Release artifacts contain only intended Android ABIs, local extension
   code, and declared native-host packages."*
   → **1a** (extension artifact file-set inline expected-list assertion in
   `test/bundle.test.ts`, plus `manifest-guard.test.ts`), **1b** (APK ABI
   inspection via `unzip -l` or `apkanalyzer` in 1d's verify image), **1c**
   (bridge package file-set snapshot).
4. *"Platform signing can consume CI-provided credentials without embedding
   secrets."*
   → **OTP-25.** OTP-01 produces unsigned artifacts only; signing,
   notarization, and the CI-credential plumbing that consumes them are
   OTP-25's scope. OTP-01 contributes the unsigned-artifact shape and the
   no-embedded-secrets guarantee (nothing in 1a/1b/1c ever writes a
   credential to disk or to logs). OTP-01 is not sufficient evidence for
   this clause and does not attempt to be.
5. *"Signed outputs are verified for provenance and content correspondence
   but are not required to be byte-identical."*
   → **OTP-25.** The signed↔unsigned comparison procedure is defined and
   exercised once real signing exists. OTP-01 prepares the ground by
   producing stable unsigned reference artifacts whose bytes can later be
   compared against a signature-stripped signed build.
6. *"No runtime download or remote executable code is introduced."*
   → **1a / 1b / 1c** — enforced by: exact-pinned `package.json` with
   committed lockfile (no caret ranges), no `curl \| sh` or `npx` in any
   Gradle task, Tauri's `windows = []` preventing updater wiring, the
   manifest/CSP baseline (no remote script sources), and a license/SBOM scan
   in 1d that fails the build if any dependency declares a network-fetch
   install-time command.

### Decomposition-specific criteria (added for 1a–1d sequencing, not in the RFC)

7. Byte-determinism of `web-extension/dist` → zip → sha256 sidecar is
   demonstrated on the authoring machine **and** inside the pinned Docker
   verify-image before 1d closes (the actual cross-environment byte-compare
   gate that clause 1 requires).
8. The `web-extension` CI job runs `npm run format:check`, `npm run lint`,
   `npm run typecheck`, and `npm test`; build/bundle/package checks remain
   explicit npm entry points and never enter APK assembly.
9. Beginning with 1b, root `./gradlew clean` removes `web-extension/dist/` and
   `web-extension/rust-wasm/pkg/` in addition to root/app `build/` outputs.
10. Root `./gradlew check` runs `rustFormat`, `rustLint`, and `rustTest`;
    clean APK assembly runs `rustJni` automatically and packages exactly the
    three approved ABIs.

## Error-handling rules (global)

- No Gradle task performs an unpinned network fetch. The allowed build-time
  fetches are `npm ci`, locked workspace Cargo resolution, and exact-version
  `cargo install --locked` into `build/rust-tools/`. Gradle never downloads
  Rust, rustup, an NDK, or an unversioned executable.
- Clean failure fast: missing tool → exit code 2-equivalent message
  naming the missing tool and the pinning file that should have provided
  it.
- No auto-fix: lockfile drift, format drift, lint findings all abort
  rather than rewrite.

## Out of scope (explicitly, per RFC and this decomposition)

- SPAKE2 protocol implementation (OTP-03), protocol freeze (OTP-02),
  Android BLE service (OTP-06), Chrome native-messaging connector
  (OTP-07), installers with signing (OTP-25), any UI, any OTP integration,
  any runtime download.

## Risks and open questions

- Cargo and npm lockfile byte-determinism across hosts: different OS
  line-endings or registry mirrors can produce different lockfiles from
  the same input. Mitigation: lockfiles are committed and compared
  byte-for-byte in `verify/verify-all.sh`.
- Tauri headless-mode stability (`windows = []`) is a Gate D review item;
  1c's skeleton proves the build produces the right artifact shape, not
  that the runtime behaves.
- Vite plugin pinning: some Vite plugins float on minor versions
  unless explicitly pinned; the spec mandates exact-version pinning in
  `package.json` (no caret).
- WASM loading inside an MV3 CSP is a known sharp edge
  (`'wasm-unsafe-eval'` required in `content_security_policy`). 1a's
  manifest guard hard-fails on `wasm-unsafe-eval`; 1b changes the exact CSP
  baseline to permit only that directive alongside `'self'`. A production
  extension import remains deferred, but the generated web-target package is
  executed by the 1b Node smoke test.
